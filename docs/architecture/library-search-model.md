# Library / Search Model

## Data flow

```
Raw records (DocumentRecord, SermonDocumentRecord)
    ↓ normalizeDocumentRecord / normalizeSermonRecord
HolocronDocument[]
    ↓ createSearchCorpus
HolocronSearchCorpusEntry[]   (searchableText, titleText, bodyText, tagText)
    ↓ searchHolocronCorpus
HolocronSearchResult[]        (content results: doctrine, supplemental, sermon)
    +
    ↓ searchBookmarks / searchNotes
HolocronSearchResult[]        (user-state results: bookmarks, notes)
    ↓ combineUserStateResults
Sorted, deduplicated HolocronSearchResult[]
    ↓ LibraryResults renders UI
```

## Content results vs user-state results

**Content results** come from normalized doctrine/supplemental/sermon documents.
They are generated by `searchHolocronCorpus` which operates on the search corpus.
The corpus is built statelessly from `HolocronDocument[]` — no database queries needed after initial load.

**User-state results** come from bookmarks and notes stored in IndexedDB.
They are generated by `searchBookmarks` and `searchNotes`.
Both functions take the same `HolocronSearchResult` type so the render layer (`LibraryResults`) does not need to distinguish between content and user-state results.
Bookmarks and notes reference documents by `documentId`. Missing/deleted document references are skipped silently.

## Why the same result shape?

One render path (`LibraryResults` with `library-card` / `authority-badge`) handles all result types.
The `scope` field (`doctrine` | `supplemental` | `sermon` | `bookmark` | `note`) controls the badge label.
The `href` always routes to the correct reader page via `getDocumentRoute()`.

## Search scope definitions

| Scope | Source | Authority class | Scope label |
|---|---|---|---|
| `doctrine` | `normalizeDocumentRecord` | `canonical` → `doctrine` | Doctrine Text |
| `supplemental` | `normalizeDocumentRecord` | `supplemental` | Study Text |
| `sermon` | `normalizeSermonRecord` | `sermon` | TOTJO Sermon |
| `bookmark` | `searchBookmarks` | — | Bookmark |
| `note` | `searchNotes` | — | Note |

## Current search implementation

Simple normalized substring matching:

```
normalizeSearchText(value):
  strip markdown punctuation (# > * _ ` -)
  collapse whitespace
  lowercase
  trim
```

Excerpts are generated by `createExcerpt` which finds the match position
in the original (un-normalized) text and slices a window of context around it.

## Future upgrade path

If the corpus grows beyond the current size, the search pipeline supports:

1. **IndexedDB full-text search** — Dexie's `where(...).startsWithAnyOfIgnoreCase(...)` or compound indexes could replace in-memory filtering.
2. **Web Worker** — Corpus building and search could be offloaded to a worker without changing the interface.
3. **FTS5 / SQLite** — If the app ever moves to a heavier local database, the search pipeline boundary (corpus → query → results) stays the same.
4. **Cross-document references** — `HolocronReference` is already part of the content model; a future search upgrade could include matched reference labels.

The key constraint is that `searchHolocronCorpus`, `searchBookmarks`, and `searchNotes` all return the same `HolocronSearchResult[]` type, so upgrading the search algorithm does not require changing the UI layer.
